# Gitea —— 这条场景的被测产品

`todo-*` 那四个场景测的是仓库自带的 `demo-app/`：一个单 HTML 文件、没有后端、
状态只活在 localStorage 里。它够用来解释这套纪律，但证明不了「换一个陌生界面还成不成立」。

这里放的是**另一条路**：一个真实的开源产品，有后端、有数据库、有登录态。

跑的是 [Gitea](https://about.gitea.com/)（MIT，Git 服务，86k+ star 的那个），
选它的理由很实际：

- **单文件二进制 + SQLite**，不用 Docker、不用先装数据库，一台干净的开发机一条命令就能起；
- **界面是服务端渲染的**，正文读得到、锚点稳，不靠前端框架的状态猜；
- **主流程是真有后端的**——注册、建仓库、开工单、评论、关闭，每一步都真的写库，
  正好对上这套东西的立身之本：写操作之后不回读，屏幕上的东西不算数。

## 起

```bash
targets/gitea/launch.sh          # 首次会下载二进制（约 100MB）并生成配置
```

起来之后是 `http://localhost:3100/`。二进制、数据库、仓库全在 `.run/` 下，不进 git；
`rm -rf targets/gitea/.run` 就是一台全新实例（下次启动会重新下载）。

用别的端口：`GITEA_PORT=3101 targets/gitea/launch.sh`（记得同步改场景里的地址）。

## 清理

```bash
scripts/cleanup_gitea_user.sh rb-20260930113000
```

场景每跑一次都会注册一个带时间戳的新用户；这条命令把用户连同他名下的仓库一起 purge 掉。
界面里没有删用户的入口，只能走命令行——这是 Gitea 的设计，不是这套东西的绕路。
脚本放在 `scripts/` 而不是这里，是因为 runner 的脚本沙箱只放行技能 `scripts/` 下的脚本，
清理得是它能自己跑的一步。

**为什么实例里有个 `rb-admin`。** Gitea 拒绝删除实例上最后一个管理员，而空实例上注册的
第一个账号一定会拿到管理员权限——不垫一个常驻账号的话，第一次跑批注册出来的那个用户
就永远清不掉，清理脚本时灵时不灵。`launch.sh` 会先建好这个只用来占位的管理员，
场景自己注册的用户就始终是可删的普通用户。它的密码是 `Roadbook-Admin-123`，
只绑在 `127.0.0.1` 上、场景不登录它。

## 刻意关掉的东西

`launch.sh` 生成的 `app.ini` 里关掉了**邮箱确认**和**图形验证码**：

```ini
[service]
REGISTER_EMAIL_CONFIRM = false
ENABLE_CAPTCHA = false
```

它们是真实产品里的可选配置，不是这个产品的主流程；不关掉的话每次跑批都要一台 SMTP
或者人工点一次验证码，而这条场景验的根本不是那两件事。**不要**因为关掉了它们就把
注册这一步的结论往「注册功能没问题」上写——这里验的是「注册完能不能接着干活」。
