# 场景：任务持久化（演示）

## 什么时候跑

用户说"跑一下 demo""看看基本流程通不通""演示一遍"；不确定跑哪个也先跑它。

随仓库自带的场景，让新用户五分钟内在本地看完整套闭环。被测应用是 `demo-app/`，单个 HTML 文件，没有后端。

> 这个文件只放 **runner 需要、又必须由人定** 的东西：目标、固定参数、红线、造数、清理。
> **不写步骤**——怎么走是 `playbook.md` 的活，首跑探索会自己写出来。

## 目标

在演示应用里加一个任务，让它真的被存下来，而不只是渲染出来。

## 环境

```
preview_start { "name": "demo" }        # 在 http://localhost:4173 上跑 demo-app
```

## 固定参数

- 任务标题：`发布路书演示`——别自己编文案，裁判按 `context.task_title` 去列表里对。
- 场景假定从零开始：列表非空要先清空（怎么清见原子 `reset-demo-data`）。

## 留给裁判的事实

`runs/<本次>/context.yaml` 只写你**实际输入**的标题：

```yaml
task_title: 发布路书演示
```

总数、未完成这些数**不要写**——期望值在 `expect.yaml` 里，不由 runner 转述。

## 清理

清空演示数据（按钮，或清 localStorage 的 `roadbook_demo_tasks`）。清理失败不改变结论，记录即可。

## 红线

没有。这个演示只碰 localStorage。真实场景一旦花钱、删数据、触达真人，必须在这里写死上限，
runner 在确认弹层的**文本**里读到真实数字超过上限就停（见 SKILL.md「花钱与不可逆」）。

## 故意看一次 FAIL

把同一场景跑在 `http://localhost:4173/?bug=optimistic`。该模式下新任务只渲染不写存储，
加完那一刻一切正常；裁判两屏都自己加载，会拿到 `FAIL`，证据是页面原文「还没有任务。」。
一条命令复现这套设计的全部理由：靠截图断言的话这次会被判 PASS。
