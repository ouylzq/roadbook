# 场景：Gitea 新用户主流程（开源实例）

## 什么时候跑

用户说「拿个真实产品跑一遍」「开源实例还通不通」「跑一条完整主流程看看」，
或者要给没接触过这套东西的人演示的时候。

它和 `todo-*` 那几个演示的区别：被测的是一个**真实的开源产品**（Gitea，有后端、
有数据库、有登录态），不是仓库里那个单文件 demo。同一套纪律换到一个没被它开发过的
界面上还成不成立，看这条。

## 目标

一个全新用户在这个实例上：注册成功 → 建出一个仓库 → 在仓库里开一个工单 →
在工单下评论 → 把工单关掉。仓库、工单、评论、关闭状态这四样都真的写进了服务端：
换一个页面重进、刷新之后都还在。

## 环境

本机起的 Gitea 实例，入口 `http://localhost:3100/`：

```bash
targets/gitea/launch.sh          # 起实例（首次会下载官方二进制、生成配置）
```

不需要登录配方、不需要取验证码、不需要 Tailscale：实例连它的 SQLite 一起住在
`targets/gitea/.run/` 下。

## 固定参数

- 用户名：`rb-<yyyymmddHHMMSS>`——跑的时候取当前时间戳，别自己编别的形状。
- 邮箱：`rb+<同一个时间戳>@example.com`。
- 密码：`Roadbook-Demo-123`。
- 仓库名：`roadbook-demo`。
- 工单标题：`路书回归：工单真的落库了吗`。
- 评论正文：`路书自动评论：确认这条评论落到服务端了`。
- 仓库名、工单标题、评论正文这三条裁判会照着对，别顺手改成别的文案。

## 留给裁判的事实

`runs/<本次>/context.yaml`：

```yaml
username: <你实际注册的那个用户名>
repo_name: roadbook-demo
repo_url: http://localhost:3100/<用户名>/roadbook-demo
issues_url: http://localhost:3100/<用户名>/roadbook-demo/issues?state=all
issue_url: http://localhost:3100/<用户名>/roadbook-demo/issues/1
issue_title: 路书回归：工单真的落库了吗
comment_body: 路书自动评论：确认这条评论落到服务端了
```

`issues_url` 一定要带 `state=all`：默认的工单列表只列开启中的，关掉的那条不在里面。

## 清理

```bash
scripts/cleanup_gitea_user.sh <用户名>
```

删用户会连带 purge 掉他名下的仓库、工单和评论。

**顺序不能反：清理在裁判判完之后做。** 裁判要核对的就是这个用户名下的仓库、工单和评论，
还没判就清掉，等于把证据毁了——那不是清理，那是让这次跑批变成 BLOCK。
清理失败不改变场景结论，把用户名记进报告即可。

## 红线

- 只在这个本机实例上写。它没有外网出口，也不要顺手去碰任何外部站点。
- 不要点「删除仓库」「删除账号」这类破坏性入口；清理只走上面那条命令。
- 实例已经关掉了邮箱确认和图形验证码。要是路上还是撞见没见过的验证页面，
  判 `blocked`，不要试图绕过它。
