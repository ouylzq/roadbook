# 判决纪律

## 谁判、凭什么判

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| **runner**（跑场景的 agent） | 开车；到位标志到不了就停；把基线写进 `context.yaml` | 不下任何结论 |
| **裁判**（新起的 agent） | 拿 `expect.yaml` + `context.yaml` + 已登录的浏览器，按 `judge-protocol.md` 走完路线，写 `judgment.yaml` | 不碰方向盘；看不到操作过程 |
| **`scripts/judge.py`** | 查 `judgment.yaml` 是否完备、是否与 `expect.yaml` 镜像，给退出码 | 不碰语义 |

场景结论 = `judge.py` 的退出码。**0 = PASS，1 = FAIL，2 = BLOCK，没有第四种解读。**

- 截图不是判据，"页面说保存成功了"不是判据，runner 自己的判断不是判据。
- `judgment.yaml` 里每条 `pass` / `fail` 都必须带页面原文证据。缺证据记 BLOCK，不是 PASS。
- `judge-output.txt` 是 judge.py 的逐条输出，原样进报告。

## 为什么是这个形状

- **期望写成代码会漂。** 这套设计的前身把断言放在 shell 脚本里、把期望值写在散文里，
  靠人工"两处同步"维系。真正对照的那天发现：文档里 6 条期望只有一半在脚本里存在，
  脚本的调用签名也早就和文档不一致了。现在期望只在一处、用人话写、由裁判理解，
  没有第二份可以漂。
- **界面会骗人，所以硬事实必回读。** 同一天里两个 bug 都是屏幕显示**新值**、
  后端还是旧值。两个都在刷新后露出真相——这就是协议强制"读状态/数量/金额之前先刷新"的原因。
- **裁判不能是司机。** 裁判是新起的 agent，没有操作上下文，也拿不到路书。
  这靠数据流强制，不靠 prompt 说"请客观"：runner 从不读 `expect.yaml`，
  裁判也从不读 `playbook.md`。
- **模型可以理解期望，但不许裸判。** 每个判决都锚在原文引用上，
  所以人能复核、两次 run 能对比。这就是这套设计与"自然语言断言直接返回布尔值"的分界线。

## 回读的手段

| 优先 | 方式 | 说明 |
|---|---|---|
| 1 | 刷新后 `get_page_text` | 裁判的默认手段；navigate 到同一 URL 就是刷新 |
| 2 | 产品自己的读接口 | 文本表达不精确时可选。注意网关字段名 ≠ 数据库列名，按接口写 |
| 3 | `read_page` 读 `<main>` 之外的区域 | 退守手段，在 `how` 里注明原因 |

查数据库、查日志平台**不在范围内**。路书只回答"这条流程还跑得通吗"，
不回答"为什么坏"。第二个问题交给你们团队做根因排查的那套工具。

## 共享夹具账号：裁判必须紧跟 runner

如果被测账号和别的测试套件共用，或者有定时清理任务在后面跟着跑，那结论是有保质期的。
实测过一次：隔天早上再去验前一天跑的流程，拿到 3 个 `blocked` + 1 个 `fail`——
对象被隔夜清理任务删了，余额被另外两个套件动过。**这些全都不是产品故障。**

- **runner 一结束就立刻起裁判**：同一会话、同一浏览器。
- 跑路书期间，别的东西不能动这个账号。做不到就把余额这类 check 的结论当参考，
  并在报告里注明"账号非独占"。
- 隔天再去验昨天的对象，在有清理任务的环境里没有意义。

## 先排除"假故障"：凭据压根没读到

`. .env.local`（**不带 `./`**）会让 zsh 去 `$PATH` 里找文件、找不到就静默失败。
再加个 `2>/dev/null`，连报错都看不见——token 变成空串，接口回"token 过期"。
**这不是 token 过期，是压根没读到。**

看到 401 或"过期"这类返回，先确认凭据真的读进来了：

```bash
echo "token长度=${#YOUR_TOKEN_VAR}"   # 0 就是没读到
```

source 一律带显式路径，或者走一个用绝对路径解析的辅助脚本。

## 什么算 BLOCK（环境问题，不是被测功能的问题）

- **runner 侧**：依赖不可达、人机验证被触发、环境本身 5xx 或超时 →
  写 `runs/<本次>/blocked.txt` 说明原因，**不起裁判**。
- **裁判侧**：页面挂了、登录掉了、导航不过去、文本里没有相关内容 → 该条 `blocked`。
- **记分器侧**：`judgment.yaml` 缺失、结构与 `expect.yaml` 不镜像、
  或者 `pass`/`fail` 却没有证据。
- **凭据**：401 / 403 / "过期"这类返回。先当凭据问题查，排除了才升级成 FAIL。

**runner 因为非环境原因停下**（按钮没反应、锚点找不到、回读的值不对）**照常起裁判**：
终态不满足期待，裁判自然判 `fail`，`judgment.yaml` 里会写着
"对象不存在""状态还是草稿"这样的证据。runner 停在哪一步写进报告供人对照，不进退出码。

## FAIL 之后

1. 不改被测应用的代码。
2. 把复现路径写人话——哪个入口、点了什么、看到什么 vs 该看到什么。
   直接引用 `judgment.yaml` 里的 `evidence` 和 `note`。
3. 有余力就顺手定位（读 diff、对部署时间线），并标注结论是"读码所得"还是"实测复现"。
   但**别在这里做日志取证**，那是另一套工具的活。
