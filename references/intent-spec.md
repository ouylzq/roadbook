# intent.md 书写标准

`intent.md` 是**人**写给 runner 的那份要求：这个场景要证明什么、跑在哪、哪些输入写死、
什么绝对不许做。**不写步骤**——步骤是 agent 勘出来写进 `playbook.md` 的。

这份标准的存在是为了让不写代码的人（产品经理）也能照着填出一份能跑的场景。
骨架不是谁拍的，是三处已有约束收拢起来的结果：

- `SKILL.md` 早就写了该有什么：一句话 description +「什么时候跑」+ 目标、环境、固定参数、
  红线、造数、清理；
- `scripts/scenarios.py` 在机器层面**已经**硬依赖 frontmatter 的 `name`/`description`
  和精确标题 `## 什么时候跑`——缺了不报错，是**静默**从索引里消失；
- 现存场景里最规整的那几份（`search-first-result`、`prod-login-page`）实际就是这个形状。

---

## 骨架

```markdown
---
name: <场景目录名，必须和目录一致>
description: <一句完整的话，25~120 字：被测什么、做什么、验什么>
envs: [dev]        # 可选。要跑 prod 必须在这里显式写出来
---

# 场景：<一句话标题>

## 什么时候跑
## 目标
## 环境
## 固定参数
## 前置造数        # 可选，不需要就整节删掉
## 留给裁判的事实   # 可选
## 清理
## 红线
## 待补            # 可选
```

**小节标题必须逐字一致**，顺序按上面来。看板的结构化编辑器只认这套标题；
对不上就只能按纯文本改，编辑器帮不上忙。

---

## 逐节怎么写

### frontmatter

| 字段 | 必填 | 说明 |
|---|:-:|---|
| `name` | ✅ | 和场景目录名一致。`scenarios.py` 第 1 层索引靠它 |
| `description` | ✅ | **一句完整的话，25~120 字**。挑场景时人只看得到这一句，写不清就等于没有这个场景 |
| `envs` | ⬜ | 支持哪些环境，如 `[dev, prod]`。**不写就只能跑 dev**；prod 必须显式列出 |

`description` 要同时回答三件事——被测什么、做什么、验什么。反例：「登录测试」（看不出验什么）。
正例见 `search-first-result`。

### ## 什么时候跑（必填）

用户说哪些话就该跑这个场景。写成人话，别写术语——这一段是给人挑场景用的
（`scenarios.py` 第 2 层就打印它）。

> 用户说"搜索还能用吗""点搜索结果会不会跳错""搜索主流程回归一下"。

### ## 目标（必填）

这个场景要证明哪个**业务结果**成立。不是「点到某个按钮」，是「登录成功」「项目发布成功」这种。

> 搜索结果的第一条自然结果，点进去之后落地页的内容确实跟搜索词相关，
> 不是跳到了无关页面、错误页或者广告落地页。

### ## 环境（必填）

跑在哪个环境、入口在哪、要不要先起服务。

**域名、账号、密钥一律从 `config/env.json` 取，绝不写死在这里。** 这里只写「取哪个环境」
和人需要知道的差异。

### ## 固定参数（必填）

写死的输入：搜索词、文案、选项、数量、附件内容。

**凡是没写死的，agent 就会自由发挥**，两次跑的结果没法比，裁判也没法判。
如果某个数字会被拿来当判据（比如附件里的「62%」），必须在这里写死，
并注明「改这里要同步改 `expect.yaml`」。

### ## 前置造数（可选）

跑之前要先有什么：造数脚本、已存在的项目、登录态。不需要就**整节删掉**，别留个「无」。

### ## 留给裁判的事实（可选）

跑完写进 `runs/<本次>/context.yaml`、供 `expect.yaml` 用 `context.xxx` 引用的值。

只放**跑的时候才知道**的东西：新建对象的 id、实际输入的名字、操作前的余额。
**别把「应该是多少」写进来**——那样就成了裁判按 runner 的说法判 runner。

**什么时候才需要这一节：只有「跑的时候才定下来」的值。** 判断口径很简单：

- **你写文件的时候就已经知道的值 → 不要列在这里。** 地址、固定文案、固定选项，
  在 `expect.yaml` 里**直接写那个值**就行：

  ```yaml
  # 好：地址是写死的，直接写
  - go: 打开 https://www.gov.cn/zhengce/，读「最新政策」区块

  # 坏：为写死的地址造一个变量，多一层没人看得懂的间接
  - go: 打开 context.list_url，读「最新政策」区块
  ```

- **只有跑的时候才知道的值 → 才列在这里。** 新建对象的 id、从列表里挑中的那一条的标题、
  实际输入的名字。做法是**成对**的，缺一半就会让裁判取不到值、整场判 BLOCK：

  1. 这一节写一行 `<键名>: <它是什么>`；
  2. `expect.yaml` 里用 `context.<同一个键名>` 引用它。

  键名用能自解释的英文小写下划线，两边**逐字一致**。

### ## 清理（必填）

造的数据怎么清。清不掉就写明把哪个 id 记进报告。全程只读就写「不需要」加一句为什么。

### ## 红线（必填）

**绝对不许做的事**。这一节是给 agent 的刹车，写得越具体越好：

- 花钱：必须写死一个上限，或者写明「本场景全程免费，看到发布按钮直接忽略」
- 删数据、发布、触达真人：明确禁止
- 验证码 / 人机校验：一律判 `blocked`，不许尝试去解

### ## 待补（可选）

这个场景还没覆盖到、下次值得补的部分，以及踩过的坑留档。写在这里是为了不丢，
不影响这次能不能跑。没有就整节删掉。

> - 多附件、非 .md 类型都没试过。
> - 2026-09-08 首跑判 FAIL 是验收标准定得不合理，已改 `expect.yaml`。

## 三条硬规矩

1. **不写步骤。** 「先点 A 再点 B」属于 `playbook.md`，由 agent 勘出来。
   intent 写「要达成什么」，不写「怎么达成」。
2. **不写期望值。** 「应该显示 3 条」属于 `expect.yaml`。runner 读 intent、裁判读 expect，
   两个读者互不交叉——这是裁判分离在文件层面的形状。
3. **不写工具名。** `click`、`browser_navigate` 这类是运行时的事。
   写「打开页面」「点提交」，换个运行时才还能跑。

## 自检

写完对一遍：

- [ ] `description` 一句话说清了被测什么、做什么、验什么，25~120 字
- [ ] 六个必填小节都在，标题逐字一致
- [ ] 目标写的是业务结果，不是界面动作
- [ ] 所有会影响结果的输入都在「固定参数」里写死了
- [ ] 「留给裁判的事实」里只有跑的时候才知道的值；写死的地址/文案没有被造成变量
- [ ] 这一节里每个键名，都在 `expect.yaml` 里用同名 `context.<键名>` 引用（不多不少）
- [ ] 红线里写清了花钱 / 删数据 / 触达真人的边界
- [ ] 通篇没有步骤、没有期望值、没有工具名

看板上「改要求」按钮里的表单就是照这份标准生成的，填完自检项也就过了。
